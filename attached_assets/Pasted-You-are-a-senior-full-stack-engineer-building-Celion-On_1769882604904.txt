You are a senior full-stack engineer building Celion One V1 for Cellion Platforms.

GOAL (V1)
Build a production-ready web app MVP called “Celion One” that helps users (founders) complete a single digital intake for Nigeria company incorporation + post-incorporation, verify identity/documents once, and route execution to a lawyer portal. Even if final filing is physical, the user experience must be seamless, tracked, and auditable. Lawyers upload stamped originals after completion and handle courier shipment of originals to the user. The platform stores a reusable “Company Vault” for future workflows (TIN, bank account opening referrals) – these can be marked “Coming Soon” but the data structures and UI scaffolding should exist.

IMPORTANT: V1 MUST ALSO BE AN INSTALLABLE PROGRESSIVE WEB APP (PWA) with offline-resilient drafting and upload queuing (details below). Do NOT promise offline final submission. Offline is for drafting + resilient uploads only.

STACK (RECOMMENDED)
- Backend: Python Flask
- ORM: SQLAlchemy + Flask-Migrate
- Auth: Flask-Login (session-based)
- Security: Flask-Talisman + CSRF protection + rate limiting (Flask-Limiter)
- Storage: Local filesystem for dev, abstraction layer for S3-compatible storage later
- Frontend: Jinja templates + Tailwind (preferred) or Bootstrap 5 with clean UI
- Background jobs: APScheduler optional; keep synchronous for V1 unless needed
- Payments: Paystack (Nigeria) for user checkout + split payout to lawyers (Paystack subaccounts).
  If split payout isn’t feasible in sandbox, implement the full ledger + webhook handling and stub transfer behind an interface.
- AI: OpenAI API for “Legal AI” mapping business description -> CAC activity suggestions
- PWA: service worker + manifest + IndexedDB for offline drafts and upload queue.

NON-NEGOTIABLES
1) Strong separation: Founders submit data; lawyers cannot modify founder identity/critical fields; lawyers can only request changes or add notes.
2) Audit everything: view/download/upload/status-change actions logged.
3) Sensitive data security: strict access control; private file links; no public URLs; no sensitive docs cached offline by default.
4) Consent model: user must explicitly consent for a lawyer to access their application.
5) Feature flags: allow enabling/disabling “Coming Soon” modules without code changes.

CORE V1 USER ROLES
- Founder (end user)
- Lawyer (processing agent)
- Admin (platform operator)

PRIMARY V1 WORKFLOWS
A) Founder onboarding -> Identity verification -> Create application -> Upload documents -> Pay -> Submit -> Track status -> Receive completion + digital vault
B) Lawyer portal -> View assigned applications -> Review checklist -> Request clarification -> Mark “Filed (Physical/Digital)” -> Upload stamped originals -> Create courier shipment -> Mark complete
C) Admin portal -> Manage lawyers, assignments, pricing, feature flags, view audit logs

DATA MODEL (CREATE THESE TABLES)
1) User

3) LawyerProfile

   - liveness_score (nullable), notes
   - verified_at

5) CompanyApplication
   - id, founder_user_id (FK)
   - application_type: incorporation / post_incorporation
   - status: draft/submitted/under_review/clarification_requested/filed/pending_originals/courier_in_transit/completed/rejected
   - company_name_1, company_name_2, company_name_3 (optional)
   - business_description (text)
   - legal_ai_activity_suggestions (JSON)
   - selected_activities (JSON)
   - company_type (LLC etc)
   - registered_address (structured or FK to Address table)
   - directors/shareholders data (JSON for V1; normalize later)
   - assigned_lawyer_user_id (FK User)
   - submitted_at, completed_at
6) ApplicationChecklistItem
   - id, application_id (FK)
   - key (e.g. "passport_photo", "id_doc", "address_proof", "director_details")
   - label, required (bool)
   - status: missing/provided/accepted/rejected
   - reviewer_notes
7) DocumentFile
   - id, owner_user_id (FK)
   - application_id (nullable FK)
   - category: identity/company/filing/stamped_originals/courier
   - doc_type: passport, nin, utility_bill, cac_form, stamped_certificate, etc
   - filename, storage_path, sha256_hash
   - size_bytes, mime_type
   - is_sensitive (bool default true)
   - created_at
8) Payment
   - id, application_id (FK)
   - provider: paystack
   - amount_total_kobo, currency
   - breakdown_json: platform_fee, lawyer_fee, government_fee, courier_fee
   - status: initialized/success/failed/refunded
   - paystack_reference, paid_at
9) PayoutLedger
   - id, payment_id (FK)
   - lawyer_user_id (FK)
   - amount_kobo
   - status: pending/queued/sent/failed
   - provider_ref (nullable)
10) CourierShipment
   - id, application_id (FK)
   - courier_name, tracking_number
   - ship_from (lawyer firm address), ship_to (user provided)
   - status: not_started/label_created/dispatched/in_transit/delivered
   - updated_at
11) ConsentGrant
   - id, founder_user_id (FK)
   - lawyer_user_id (FK)
   - application_id (FK)
   - scope: view_documents/view_identity/process_application
   - granted_at, revoked_at
12) AuditLog
   - id, actor_user_id (FK)
   - action: login/logout/view_application/upload_document/download_document/change_status/request_clarification/admin_override etc
   - entity_type, entity_id
   - ip_address, user_agent
   - created_at
13) FeatureFlag
   - id, key, is_enabled, description
14) OfflineDraft
   - id, founder_user_id (FK)
   - application_id (nullable FK)
   - client_draft_id (string UUID from browser)
   - draft_json (JSON)  [non-sensitive form fields only; do NOT store doc blobs]
   - last_synced_at
   NOTE: IndexedDB is primary offline store; this server table is for optional sync and recovery.

UPLOAD QUEUE (RESILIENT DOC UPLOADS)
